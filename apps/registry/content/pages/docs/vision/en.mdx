# Vision

VLLNT UI is the UI layer that every vllnt product is built on: the web today, React Native at canary, desktop and spatial next. The aim is to be the fastest way for people and AI agents to build interfaces. The vllnt brand is the default theme, and every component meets WCAG 2.2 AA.

We think interfaces are changing in two ways, and we want VLLNT UI to be the foundation for both.

## Platforms

VLLNT UI is meant for every kind of interface. This is where each target stands today.

- **Web (React DOM, Next.js): shipped.** `@vllnt/ui` is on npm, with stable releases and a canary on every change.
- **Mobile, React Native (iOS, Android, Expo): canary.** `@vllnt/ui-native` publishes canary builds only; there is no stable release yet. Each canary is installed in a clean Expo app and exported for iOS and Android before it counts. See [Native](/native).
- **Desktop, Electron and Tauri: roadmap.** Nothing desktop-specific exists yet: no desktop tests, packaging or guidance.
- **Desktop, native macOS apps: roadmap.** There is no SwiftUI or AppKit renderer.
- **AR and spatial, visionOS and WebXR: proposal.** The spatial foundations are an open RFC ([vllnt/ui#631](https://github.com/vllnt/ui/issues/631)). There is no spatial renderer.
- **AI-generated, streamed UI: partly shipped.** Descriptors, the MCP server, themes as data and streaming components exist; the json-render and AI SDK adapters do not ([vllnt/ui#672](https://github.com/vllnt/ui/issues/672)).

## One core, one renderer per platform

The rule that makes this possible: the core stays platform-neutral, and each platform is a renderer on top of it.

- **The core** holds what every platform shares: design tokens, component contracts (the names of options and props), platform rules and, later, the props schemas behind each descriptor. It has no runtime dependencies and does not import any renderer.
- **A renderer** turns the core into real components for one platform: `@vllnt/ui` for the web and `@vllnt/ui-native` for React Native today, and desktop, macOS, visionOS or WebXR renderers later.
- **Dependencies point one way.** Renderers depend on the core, never the reverse, and one renderer never imports another. A decision two platforms share goes into the core first.

Today, the native package reads its tokens and contracts from `@vllnt/ui-core`, and the web package gets the same tokens as generated CSS. Moving the props schemas into the core is on the roadmap.

## 1. Spatial interfaces

AR and spatial devices place UI in the room around you, not on a flat screen. The pieces stay the same: buttons, lists, dialogs, text. What changes is depth, how you point (hand, gaze, voice) and how big a target needs to be.

The goal is that the same components and tokens render on a phone, on a laptop and in space, without a separate kit for each.

## 2. Dynamic, AI-composed UI

More and more, an interface won't be designed once and shipped to everyone the same. A model or a server will compose it at runtime from known parts, stream it to the screen as it is generated, fit it to the person using it, and update it without waiting for a new app release.

For that to work, the parts have to be:

- **Describable:** an agent can find a component, read what it does and which props it takes, and use it correctly.
- **Data-driven:** a component is fully set by its props, and a theme is data, so both can be sent over the wire.
- **Stream-safe:** a screen holds its layout while content is still arriving.
- **Safe to update:** a new version doesn't break the screens already built on the old one.
- **Accessible by default:** a generated screen meets WCAG 2.2 AA just like a hand-built one.

## Working with the Vercel AI stack

We want VLLNT UI to be first-class with two open tools from Vercel:

- **[json-render](https://github.com/vercel-labs/json-render):** you define a catalog of components, each with a zod props schema and a description. The model emits a JSON spec (streamed as JSON patches), and a renderer turns it into React. A VLLNT UI catalog would let models build screens out of VLLNT UI components.
- **[AI SDK](https://ai-sdk.dev) generative UI:** a tool call arrives in `useChat` as a message part of type `tool-<name>`, with a state (`input-streaming`, `input-available`, `output-available`, `output-error`) that maps to loading, result and error views. The AI SDK also offers `streamUI` for React Server Components, which its docs mark as experimental.

**Today** no adapter ships. VLLNT UI components are plain React components, so you can already render AI SDK message parts with the AI family (`AIStreamingText`, `Reasoning`, `AIToolCallDisplay`, `AISourceCitation`, `ApprovalRequest` and more) in your own code. **Next** is a json-render catalog, zod prop schemas for every component, and helpers that map AI SDK tool parts to components with their loading and error states: [vllnt/ui#672](https://github.com/vllnt/ui/issues/672).

## What ships today

- **Describable components.** Every component has a JSON descriptor at `/r/<name>.json`, indexed in `/r/registry.json`. Agents can also use `/llms.txt`, `/llms-full.txt` and the MCP server at `/mcp` (`search_components`, `get_component`, `list_categories`). Every descriptor carries its version and stability; prop definitions and usage examples exist for only a few components so far. See [Agents](/docs/agents).
- **Tokens and themes as data.** One token source generates the CSS variables, the product themes (switched at runtime with `data-theme`), the React Native tokens and the Penpot libraries. See [Theming](/docs/theming).
- **Streaming-ready parts.** `Skeleton` for loading states; `AIStreamingText`, `Reasoning`, `ThinkingBlock` and `AgentActivity` for output that arrives piece by piece. Components work with React Server Components, and client components are marked `"use client"`.
- **Safe updates.** Semantic versioning, a canary build on every change to `main`, stable releases only from reviewed tags, the `latest` tag never moves backwards, and every release lists its upgrade notes. See [Changelog](/docs/changelog).
- **Accessibility gate.** Every story is tested with axe against WCAG 2.0 to 2.2, levels A and AA, in light and dark themes. Any violation fails the build.
- **Shared core for more than one renderer.** `@vllnt/ui` (web) and `@vllnt/ui-native` (React Native) are generated from the same tokens and component contracts; the native package reads them from `@vllnt/ui-core`. Every interactive native component shares one affordance primitive for its pressed, hovered, focused and disabled states. See [Native](/native).

## On the roadmap

None of these ship yet. They are the next steps toward the vision.

- **Spatial foundations** (proposed for 0.5.0): depth tokens, one affordance contract for pointer, touch and gaze, target sizes that adapt to the input (24 px pointer, 44 pt touch, 60 pt spatial), and motion tokens. The proposal is an open RFC: [vllnt/ui#631](https://github.com/vllnt/ui/issues/631).
- **Spatial renderers** such as visionOS or WebXR, built on the same core.
- **A complete props schema** for every component, so a model can produce a valid UI tree and a renderer can check it before showing it.
- **A partial-props contract,** so any component can render from incomplete, streamed data.
- **Per-user themes resolved at runtime,** kept inside the accessible token ranges.
- **Codemods and a written deprecation window,** so updates can be applied automatically.
- **Accessibility checks on generated UI trees,** run before a generated screen is shown.
- **json-render catalog and AI SDK helpers** for VLLNT UI ([vllnt/ui#672](https://github.com/vllnt/ui/issues/672)).
