VLLNT UI: agent-first architecture

One component kit that an AI agent can create with, extend, test and monitor, for web, native, desktop and spatial apps, in every major framework.

Status: proposal, not adopted Date: 2026-11-26 Audience: AI agents working in or with this repository

1. Goal

Build any app from one kit, with an AI agent doing most of the work and proving that the work is correct.

PropertyWhat it means hereHow we know
Agent-firstAn agent can find, use and build components from files and commands, without a person explaining.Agent task evals (#734).
ExtensibleA new component, variant, token, platform, framework or screen is added as an entry. Nothing is forked.Adding one needs no change to existing components.

4. Frameworks and renderers

The aim is the widest framework support for a bounded cost. A definition names platforms, never frameworks. A framework is supported by adding a renderer, so no component definition changes when one is added.

  • The registry lists, per component, which renderers have it. An agent reads that before choosing a component.

4.3 Framework adapter

Components must not import a router. The app passes one in. This removes the stub workaround for React apps that do not use Next.js.

// PROPOSED. UIProvider and the adapters do not exist yet.
import { UIProvider } from "@vllnt/ui";
import { tanstackRouter } from "@vllnt/ui/adapters/tanstack-router";

<UIProvider adapter={tanstackRouter}>{app}</UIProvider>

Adapters to ship: Next.js, TanStack Router, React Router, Expo Router, and plain links as the default.

4.4 Order of work

  1. Framework adapter. Fixes a gap that exists today and needs nothing else.
  2. Style recipes moved out of the React components. Every later web renderer reuses them.
  3. Web Components renderer. One build reaches every framework that has no renderer of its own.
  4. Vue, then Svelte, then Solid. Each is a generator target plus one CI column.

4.5 Cost and limits

  • Each renderer adds a generator target, a CI column, a docs tab and a published package to maintain.
  • A component with custom layout needs one layout file per renderer. Keep custom layout rare.
  • Renderers for Vue, Svelte, Solid and Web Components depend on ui-sdk adapters that are in beta.
  • Affordable only after components are generated from definitions (section 5). Writing 300 or more components by hand per framework is out of scope.

5. The component definition

Proposed The whole architecture turns on one idea: a component is described once, as data, and everything else is derived from that description.

Today a web component is several hand-written files (for example Combobox: source, story, unit test, visual test, docs page, meta.json, props.json, examples.json), and the native version is written separately. The definition replaces the parts of those files that only repeat facts.

5.1 Example

// environment-picker.def.ts
// PROPOSED. defineComponent does not exist yet.
import { defineComponent } from "@vllnt/ui-core";

export const environmentPicker = defineComponent({
  name: "environment-picker",
  purpose: "Pick one deployment environment from a searchable list.",

  // L3: which behaviors it is made of
  behaviors: ["popup", "selection", "typeahead"],

  // L2: the public contract
  props: {
    value:   { type: "string", controlled: true },
    options: {
      type: "list",
      of: { value: "string", label: "string", status: ["live", "failed"] },
    },
    disabled: { type: "boolean", default: false },
  },
  states: ["closed", "open", "disabled", "empty"],

  // L4: which kit parts draw it
  parts: {
    trigger: { uses: "Button", variant: "outline", placeholder: "Select environment" },
    search:  { uses: "CommandInput", placeholder: "Search" },
    item:    { uses: "CommandItem", shows: ["statusDot", "label", "check"] },
    empty:   { text: "No environment found" },
  },

  // L1: token names only. An unknown name is a compile error.
  tokens: {
    statusDot: { live: "status.success", failed: "status.danger" },
  },

  // Runtime: how another agent finds and operates it
  agent: { label: "Environment", actions: ["setValue", "open"] },

  // Platforms, not frameworks. Each framework is a renderer (section 4).
  platforms: ["web", "native"],

  // Regression tests, as data
  cases: [
    {
      name: "keeps focus on the trigger after picking",
      steps: [{ open: true }, { type: "prod" }, { press: "Enter" }],
      expect: { value: "production", focus: "trigger", open: false },
    },
  ],
});

5.3 What is written and what is generated

Written by a person or agent
  • <name>.def.ts
  • A layout file per renderer, optional, for custom layout only
→
Generated
  • One component per renderer: React and React Native first, then the others in section 4
  • Stories: one per variant and state
  • Unit, keyboard, accessibility and parity tests
  • Visual test matrix
  • Docs page, with web and native together (#728)
  • Registry entry and MCP answers (#728)
  • Agent bridge registration (#732)

Limit. Layout that the parts cannot express still needs an optional layout file for each renderer. That file gets hand-written tests. A renderer with no layout file for such a component does not ship it, and the registry says so.

Limit. Code and tests come from the same definition, so a wrong definition gives wrong tests that pass. Keyboard and accessibility expectations therefore come from the behavior (a popup closes on Escape), never from the definition.

5.4 Who writes what

The agent writes the definition. A generator writes the component for every renderer, automatically. The agent does not write the web and native versions.

FileWritten byWhen
DefinitionAgent or personAlways
Cases inside the definitionAgent or personFor each bug fixed and each behaviour worth keeping
Layout file for one rendererAgent or personOnly for a part marked as custom layout
Component code for React, React Native and every other rendererGenerator, automaticEvery build
Stories, tests, visual matrix, docs page, registry entryGenerator, automaticEvery build
  • The generator is a normal program, not an AI model. The same definition always gives the same output, so it can be reviewed once and trusted after.
  • Never edit a generated file. Each one starts with a header that says so, and CI regenerates everything and fails on any difference.
  • When the generator cannot express something, write a layout file, or extend the generator so every component gains the feature.
  • One fix reaches every component. A bug in how a popup is rendered is fixed once in the generator, not in each component.
  • Until the generator exists, each renderer is written by hand, as today.

6. Agent lifecycle and playbooks

1. CreateWrite one definition.
2. ExtendAdd an entry to it.
3. TestRun one gate.
4. ShipOpen a pull request with the visual diff.
5. MonitorRead the running UI and the drift reports.

Commands marked Planned are on the roadmap as agent-ui-cli. Commands marked Proposed exist only here.

6.1 Create a component

  1. Search first. Ask the MCP server (search_components) or read /r/registry.json. Do not build what exists. Live
  2. Load the rules, tokens and component index: vllnt-ui context --json. Planned
  3. Write <name>.def.ts. Use only token names and kit parts. Proposed
  4. Generate the outputs: vllnt-ui generate <name>. Proposed
  5. Run the gate: vllnt-ui gate. It returns one pass or fail, the same locally and in CI. Planned
  6. Look at the new screenshots and accept them.
  7. Open a pull request. Report what passed and what you could not verify.

6.2 Extend a component

  1. Add the variant, state, prop or platform to the definition. Do not copy the component.
  2. Generate and run the gate.
  3. Expect the visual diff to show only new screenshots and zero changed ones. A changed screenshot means the extension altered existing behaviour.

6.3 Fix a bug

  1. Add a cases entry that describes the bug. Run it and see it fail.
  2. Fix the cause.
  3. See the case pass on every platform in platforms. The case stays for good.

6.4 Add a platform or a framework

  1. For a platform, add its name to the platform list in @vllnt/ui-core. For a framework, skip this step.
  2. Create a renderer package: the behaviors adapter, the shared style recipes, a template generator, and a framework adapter. Import only from L1 to L3.
  3. Add a CI column that runs the parity suite on it.
  4. Change no component definition. Components with custom layout join the renderer when someone adds their layout file.
  5. List the renderer in the registry only after the parity suite passes (R12).

6.5 Monitor an interface

  1. Read what is on the page through the agent bridge snapshot. #731, #732
  2. Act by label, then read back the values that took effect.
  3. Read the readiness report: vllnt-ui status --json. Planned
  4. Read the scheduled visual drift report for the deployed app. Proposed

9. Visual regression

9.1 Today

  • 243 visual test files exist for the web kit, and 34 baseline images are stored in the repository.
  • The CI job runs them with --update-snapshots. That rewrites the baseline on each run, so the job cannot fail on a visual change.
  • The native kit has no visual tests.

9.2 Design

  1. Compare base against head. CI builds the stories for the base branch and for the pull request, takes the same screenshots of both, and diffs them. No baseline images are stored in the repository.
  2. Make rendering repeatable. Fix the clock, the random seed, animations, fonts and the viewport. Wait for images. A story that cannot be made repeatable is tagged and excluded by name, never silently skipped.
  3. Take the matrix from the definition. Each variant, state, theme and width is one screenshot. Open, hover and focus states are included for interactive parts.
  4. Report three lists. New, changed and removed. New screenshots do not fail. Changed and removed ones fail.
  5. Accept on purpose. A changed screenshot passes only after a person or agent accepts it with a recorded reason. Nothing updates itself.
  6. Same flow on native. Screenshot the catalog app per component and state.

9.3 Adding visual regression for a component

There is no step. Adding a variant or state to the definition adds its screenshots to the matrix.

9.4 Done when

  • A deliberate one-pixel change to one component fails CI and names that component.
  • Running the same commit twice gives zero differences.
  • The report shows new, changed and removed lists on the pull request.

13. Definition of done

The architecture is in place when each line below is a check that passes.

  • A new component is one definition file, plus an optional layout file per platform.
  • Every declared variant, state and theme has a screenshot, and a missing one fails the gate.
  • A deliberate one-pixel change fails CI.
  • The same cases pass on web and native for every component that lists both.
  • An unknown token name does not compile.
  • An agent with only the shipped docs passes the agreed share of eval tasks.
  • An agent fills a form by label on web and on native without a screenshot.
  • Adding a platform or a framework changes no existing component definition.
  • A React app without Next.js installs and builds with no stub files.
  • Every listed framework passes the parity suite in CI.
  • CI regenerates all generated files and finds no difference.

15. Glossary

WordMeaning
TokenA named design value, such as a colour or a spacing step.
ContractThe platform-neutral description of a component: its props, states and accessibility role.
BehaviorAn interaction with no styling, such as a popup, a selection or type-to-search.
RendererThe package that draws components for one framework.
AdapterA small object that gives components the app's link, image and navigation.
RecipeThe map from a variant to its class names, shared by every web renderer.
GeneratorA program that writes component code, tests and docs from a definition. Not an AI model.
PartA named piece of a component, such as the trigger or an item.
DefinitionThe one file that describes a component as data.
CaseA scripted scenario with an expected result, used as a regression test.
ParityThe same component behaving the same on every platform it supports.
BridgeThe runtime link that lets an agent read a page's components and call their actions.
GateOne command that returns a single pass or fail for all checks.
